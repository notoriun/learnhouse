# Recursos Customizados e Webhooks

O [guia de construção](/guides/build-learning-platform) mostrou como *ler* a API como um
frontend. Este guia é sobre ir mais além: controlar o Notoriun **programaticamente** — criando e
gerenciando conteúdo a partir dos seus próprios scripts e serviços, e reagindo ao que acontece
dentro do Notoriun com **webhooks**.

<GuideCards set="custom" />

## Duas formas de autenticar

| | Sessão de usuário (JWT) | Token de API |
| --- | --- | --- |
| **Para** | Agir *como um usuário conectado* (um frontend) | Automação servidor-a-servidor, scripts, integrações |
| **Como** | `POST /api/v1/auth/login` → token bearer | Um token de longa duração criado nas configurações da organização |
| **Prefixo** | um JWT | `lh_…` |
| **Plano** | qualquer | **Pro** |

Para tudo neste guia, use um **token de API**. É uma única credencial bearer que você anexa a
toda requisição:

```bash
curl "http://localhost:1338/api/v1/courses/org_slug/{org_slug}/page/1/limit/10" \
  -H "Authorization: Bearer lh_your_api_token_here"
```

<Callout type="warning">
Tokens de API funcionam em rotas de recurso (courses, chapters, activities, collections…) mas
**não** em rotas que exigem uma sessão de usuário real — `/users/*`, `/orgs/*`, `/roles/*`, e a
**gestão de webhook** todos rejeitam tokens `lh_` com `403`. Use uma leitura de courses para
testar rapidamente um token.
</Callout>

### Criando um token de API

Tokens de API são um recurso **Pro**. Crie um nas configurações da sua organização, ou via a
própria API (com uma sessão de usuário que tenha permissões `roles`):

```bash
curl -X POST "http://localhost:1338/api/v1/orgs/{org_id}/api-tokens" \
  -H "Authorization: Bearer <user_jwt>" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "My integration",
    "description": "Server-side automation",
    "expires_at": null
  }'
```

A resposta inclui o **token completo exatamente uma vez** — armazene-o com segurança, ele não
pode ser recuperado novamente:

```json
{
  "token": "lh_8f3c…the only time you'll see this…",
  "token_uuid": "apitoken_…",
  "name": "My integration",
  "token_prefix": "lh_8f3c4d2a",
  "org_id": 1
}
```

<Callout type="info">
Tokens suportam permissões granulares via um objeto `rights` (escopos de leitura/escrita por
recurso) e um `expires_at` opcional. Defina `rights` para conceder a um token só o acesso de que
ele precisa. O esquema completo está no Swagger UI interativo em `http://localhost:1338/docs`
(modo de desenvolvimento). Liste, revogue, e regenere tokens sob `/api/v1/orgs/{org_id}/api-tokens`.
</Callout>

## Convenções de requisição

Algumas coisas que valem em toda a API:

- **Caminho base** — todo endpoint está sob `/api/v1/`.
- **Autenticação** — `Authorization: Bearer <token>` (JWT ou token `lh_`).
- **Leituras são JSON** — `GET` retorna JSON; listas são arrays simples a menos que documentado
  de outra forma.
- **Escritas costumam ser multipart** — endpoints de criação/atualização que podem receber um
  arquivo (courses, activities, avatars) aceitam `multipart/form-data`, não JSON. Endpoints sem
  arquivos (collections, trails, users) recebem JSON.
- **Erros** — respostas não-2xx são `{ "detail": "..." }`. Sempre leia `detail`.
- **UUIDs vs ids** — recursos expõem um `{resource}_uuid` estável (ex.: `course_…`,
  `activity_…`); ids numéricos são usados por algumas rotas (notavelmente `org_id`).

## Receita: criar um curso programaticamente

Cursos são criados com dados multipart form (para que uma miniatura possa acompanhar). `org_id`
é um parâmetro de query:

```bash
curl -X POST "http://localhost:1338/api/v1/courses/?org_id=1" \
  -H "Authorization: Bearer lh_your_api_token" \
  -F 'name=Introduction to Python' \
  -F 'description=A beginner-friendly Python course' \
  -F 'about=Learn Python from scratch.' \
  -F 'public=true'
```

<Callout type="info">
`name`, `description`, e `about` são todos obrigatórios na criação do curso — omitir `about`
retorna `422`. Criar cursos, capítulos, e atividades exige um papel com permissão de criação
(Admin / Maintainer / Instructor), não uma conta de membro simples.
</Callout>

Depois adicione estrutura — um capítulo (JSON), depois atividades dentro dele:

```bash
# Cria um capítulo
curl -X POST "http://localhost:1338/api/v1/chapters/" \
  -H "Authorization: Bearer lh_your_api_token" \
  -H "Content-Type: application/json" \
  -d '{ "name": "Getting started", "org_id": 1, "course_id": 42 }'
```

<Callout type="info">
Para criação de curso em massa ou assistida por IA a partir de mídia existente, veja os guias de
[Migração](/developers/migration) — há um fluxo de três chamadas que constrói toda uma árvore de
curso em uma transação.
</Callout>

## Receita: buscar e listar conteúdo

```bash
# Lista paginada de cursos
curl "http://localhost:1338/api/v1/courses/org_slug/{org_slug}/page/1/limit/20" \
  -H "Authorization: Bearer lh_your_api_token"

# Busca de texto completo (máx. 50 por página)
curl "http://localhost:1338/api/v1/courses/org_slug/{org_slug}/search?query=python&page=1&limit=10" \
  -H "Authorization: Bearer lh_your_api_token"
```

## Descoberta: a especificação OpenAPI

Como a API é construída com FastAPI, uma especificação legível por máquina completa está
disponível:

- **OpenAPI JSON** — `http://localhost:1338/openapi.json` (servido em todas as instâncias)
- **Swagger UI** — `http://localhost:1338/docs` (só modo de desenvolvimento)
- **ReDoc** — `http://localhost:1338/redoc` (só modo de desenvolvimento)

Aponte um gerador de cliente para `openapi.json` para produzir um SDK tipado na sua linguagem de
escolha.

<Callout type="info">
A documentação HTML interativa (`/docs` e `/redoc`) é servida só em **modo de desenvolvimento**.
A especificação bruta `/openapi.json` é gerada pelo FastAPI e está disponível em todas as
instâncias.
</Callout>

## A seguir: reagir a eventos

Fazer polling na API para descobrir "alguém terminou um curso?" é desperdício. **Webhooks**
enviam esses eventos para você no momento em que acontecem — matrícula, conclusão, cadastros, e
mais dezenas.

→ **[Consumir webhooks](/guides/custom-features/webhooks)**
