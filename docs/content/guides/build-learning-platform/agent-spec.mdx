````markdown
# ESPECIFICAÇÃO: Construir uma plataforma de aprendizado headless na API do Notoriun

## Configuração (preencha antes de começar)
- API_BASE = http://localhost:1338/api/v1     # a URL base da sua API do Notoriun
- ORG_SLUG = your-org-slug                     # o slug da sua organização
- TEST_EMAIL = you@example.com                 # opcional, para verificar a autenticação
- TEST_PASSWORD = ********                      # opcional

## Objetivo
Construir uma plataforma de aprendizado web com Next.js (App Router + TypeScript + Tailwind)
que lê cursos e conteúdo da API REST do Notoriun e suporta cadastro, login,
matrícula, e rastreamento de progresso de usuário. Construa em dois estágios:
o Estágio 1 é totalmente anônimo (sem tokens); o Estágio 2 adiciona autenticação
por cima sem reescrever o Estágio 1.

## Regras rígidas
- Os tokens de acesso/refresh do Notoriun NUNCA DEVEM alcançar o navegador. Faça todas
  as chamadas autenticadas do servidor (Route Handlers / Server Actions) e
  armazene os tokens no próprio cookie httpOnly do app Next.js (um padrão "BFF").
- Leia a base da API e o slug da organização de variáveis de ambiente; nunca as fixe no código.
- Todas as respostas de API devem ser tratadas como não-cacheáveis (cache: 'no-store').
- Exponha erros de API: os corpos de erro têm o formato JSON { "detail": "..." }.

## Contrato de API (use exatamente estes; todos os caminhos são relativos a API_BASE)
Leituras anônimas (nenhum header Authorization necessário para conteúdo público e publicado):
- GET  /orgs/slug/{ORG_SLUG}
    -> objeto da organização incluindo o `id` numérico.
- GET  /courses/org_slug/{ORG_SLUG}/page/{page}/limit/{limit}
    -> ARRAY JSON de cursos. Cada um: { course_uuid, name, description,
       thumbnail_image, public, published }. `course_uuid` já inclui um
       prefixo "course_" — use-o literalmente em URLs.
- GET  /courses/{course_uuid}/meta
    -> curso + { org_id, chapters: [ { chapter_uuid, name, description,
       activities: [ { id, activity_uuid, name, activity_type,
       activity_sub_type, content, published } ] } ] }.
       Cada atividade tem TANTO um `id` numérico QUANTO um `activity_uuid` string.
       Case o progresso com o `id` numérico (step.activity_id === activity.id);
       use `activity_uuid` para roteamento/busca.
- GET  /activities/{activity_uuid}
    -> uma única atividade { id, activity_uuid, name, activity_type,
       activity_sub_type, content, published }.
       activity_type é um de: TYPE_VIDEO, TYPE_DOCUMENT, TYPE_DYNAMIC,
       TYPE_ASSIGNMENT, TYPE_CUSTOM, TYPE_SCORM.

Mídia: servida a partir da RAIZ do backend (NÃO sob /api/v1) — derive uma base de mídia
removendo "/api/v1" de API_BASE. Os valores de mídia armazenados são nomes de arquivo
PUROS, não caminhos, então construa URLs escopadas por org/curso:
  - miniatura de curso: {MEDIA_BASE}/content/orgs/{org_uuid}/courses/{course_uuid}/thumbnails/{thumbnail_image}
  - vídeo hospedado:    {MEDIA_BASE}/content/orgs/{org_uuid}/courses/{course_uuid}/activities/{activity_uuid}/video/{fileId}
  - documento (pdf):     {MEDIA_BASE}/content/orgs/{org_uuid}/courses/{course_uuid}/activities/{activity_uuid}/documentpdf/{fileId}
  org_uuid vem de GET /orgs/slug/{ORG_SLUG} ou da resposta /meta (a LISTA de
  cursos não inclui org_uuid). Valores começando com http(s) são URLs S3
  completas — use como estão.

Autenticação (Estágio 2):
- POST /auth/login   Content-Type: application/x-www-form-urlencoded
    corpo: username={email}&password={password}
    -> { user: { user_uuid, username, email, ... },
         tokens: { access_token, refresh_token, expiry } }
    (Também define cookies httpOnly, mas confie no corpo para um cliente headless.)
- POST /users/{org_id}   Content-Type: application/json
    corpo: { email, password, username, first_name, last_name }  -> cria um usuário.
    (Resolva org_id via GET /orgs/slug/{ORG_SLUG}.)
- GET  /auth/refresh
    Lê o token de refresh SÓ do cookie `LH_refresh` — NÃO de um header ou
    corpo. Para renovar do servidor, envie o header: Cookie: LH_refresh={value}.
    -> { access_token, refresh_token, expiry }. O token de refresh GIRA: você
    DEVE persistir o refresh_token retornado (e o access_token) de volta na sua
    sessão, ou o próximo refresh é rejeitado como um replay (401).
- DELETE /auth/logout   Authorization: Bearer {access_token}  -> revoga a sessão.
- Chamadas autenticadas: envie o header Authorization: Bearer {access_token}.

Matrícula e progresso (Estágio 2, autenticado):
- Uma Trail (uma por usuário por organização) deve EXISTIR antes que um curso possa ser
  adicionado, ou add_course retorna 404. Ler a trilha a cria de forma lazy, então chame
  GET /trail/org/{org_id}/trail uma vez antes de POST /trail/add_course.
- GET    /trail/org/{org_id}/trail            cria a trilha de forma lazy; retorna
         { runs: [ { course, steps:[{activity_id, complete, ...}],
         course_total_steps, ... } ] } (uma run por curso matriculado).
- POST   /trail/add_course/{course_uuid}      matricula o usuário atual (a trilha deve existir).
- POST   /trail/add_activity/{activity_uuid}  marca uma atividade como concluída (cria trilha/run se necessário).

## Páginas / arquivos necessários
- src/lib/learnhouse.ts   : constantes API_BASE/ORG_SLUG, `lhFetch` (leituras públicas,
                            token opcional), helpers de URL de mídia que constroem os
                            caminhos escopados por org/curso na raiz do backend (veja
                            Mídia acima), tipos compartilhados.
- src/lib/session.ts      : sessão em cookie httpOnly (get/set/clear) + `authedFetch`
                            que tenta novamente uma vez em 401 renovando (o token de
                            refresh enviado como header Cookie: LH_refresh), persistindo
                            os tokens de acesso+refresh rotacionados de volta na sessão
                            antes de tentar novamente — veja o contrato.
- src/app/page.tsx        : catálogo de cursos (anônimo).
- src/app/courses/[uuid]/page.tsx           : detalhe do curso a partir de /meta (anônimo).
- src/app/courses/[uuid]/[activityUuid]/page.tsx : visualizador de atividade, alterna com base em
                            activity_type (video / document / dynamic).
- src/app/api/auth/login/route.ts   : POST -> /auth/login, armazena a sessão.
- src/app/api/auth/signup/route.ts  : POST -> resolve o id da organização, /users/{org_id}.
- src/app/api/auth/logout/route.ts  : POST -> /auth/logout, limpa a sessão.
- src/app/login/page.tsx            : formulário de login do cliente enviando para /api/auth/login.
- src/app/courses/[uuid]/actions.ts : Server Actions `enroll` e
                            `markActivityDone` usando authedFetch.
- Botão de matrícula na página do curso (link para /login se não houver sessão); marcas de
  progresso derivadas de GET /trail/org/{org_id}/trail.

## Ambiente
Crie .env.local:
  NEXT_PUBLIC_LEARNHOUSE_API_URL=<API_BASE>
  NEXT_PUBLIC_LEARNHOUSE_ORG_SLUG=<ORG_SLUG>

## Ordem de construção
1. Estrutura: npx create-next-app@latest . --typescript --app --tailwind --eslint --src-dir --use-npm
2. Estágio 1: lib/learnhouse.ts -> catálogo -> página de curso -> visualizador de atividade.
   PARE e verifique se o site público renderiza antes de continuar.
3. Estágio 2: session.ts -> route handlers de autenticação + formulário de login -> authedFetch ->
   ação de matrícula -> exibição de progresso.

## Critérios de aceitação (verifique contra a instância real)
1. O catálogo lista os cursos públicos da organização com miniaturas.
2. Uma página de curso lista capítulos e suas atividades publicadas.
3. Ao menos uma atividade renderiza (vídeo, documento, ou página dinâmica).
4. Um novo usuário pode se cadastrar (TEST_EMAIL) e fazer login.
5. Um usuário conectado pode se matricular em um curso e ver ao menos uma marca de
   progresso depois de marcar uma atividade como concluída.
Reporte quais critérios passam e mostre os comandos/URLs que você usou para verificar.

## Pontos de ajuste conhecidos (não chute — inspecione, depois adapte)
- As chaves de `content` da atividade variam por activity_sub_type e versão do editor. Inspecione
  um GET /activities/{uuid} real e adapte os nomes de campo do visualizador. Páginas dinâmicas
  são um documento de bloco estruturado; renderizar o JSON bruto é aceitável para uma v1.
- A mídia é servida a partir da RAIZ do backend (não /api/v1) em
  caminhos escopados por org/curso (veja a seção Mídia). Se as imagens retornarem 404, confirme
  que a base não tem /api/v1 e que você construiu o caminho completo
  orgs/{org}/courses/{course}/...; valores S3 são URLs absolutas.
- Em instâncias SaaS, o login pode exigir verificação de e-mail primeiro. Em instâncias
  self-hosted locais isso geralmente está desativado.
````
