# Visão Geral da Arquitetura

O Notoriun é um projeto multi-diretório com várias aplicações que trabalham juntas para entregar
a experiência completa da plataforma. O sistema segue uma separação clara de responsabilidades
entre o frontend, o backend e os serviços de apoio.

## Estrutura do Projeto

```
learnhouse/
├── apps/
│   ├── web/      # Frontend Next.js
│   ├── api/      # Backend FastAPI
│   ├── collab/   # Servidor de colaboração Hocuspocus
│   └── cli/      # CLI do Notoriun
├── docker/       # Helpers de Dockerfile de produção (config nginx, start.sh)
└── Dockerfile    # Imagem monolítica usada pelo assistente de instalação da CLI
```

Implantações self-hosted não têm um `docker-compose.yml` versionado. A CLI do Notoriun
(`apps/cli`) gera o `docker-compose.yml`, o `.env`, e a configuração do proxy reverso no momento
da instalação, a partir dos templates em `apps/cli/src/templates/`.

## Como Tudo Se Encaixa

A plataforma consiste em quatro aplicações apoiadas por dois serviços centrais:

- **Web (Next.js)** -- O frontend voltado ao usuário, que se comunica com a API de backend e o
  servidor de colaboração.
- **API (FastAPI)** -- O backend que lida com autenticação, gestão de curso, armazenamento,
  envios, recursos de IA, e toda a lógica de negócio.
- **Collab (Hocuspocus)** -- Um servidor WebSocket que alimenta a edição colaborativa em tempo
  real com autenticação JWT, persistência em Redis, e limites de usuário por quadro.
- **CLI (Commander)** -- Uma ferramenta de linha de comando usada para desenvolvimento local e
  tarefas de gestão.

## Serviços de Apoio

O Notoriun depende de dois serviços de apoio principais:

- **PostgreSQL 16 (pgvector)** -- O banco de dados relacional principal para armazenar todos os
  dados da aplicação, incluindo usuários, cursos, organizações e registros de atividade. Usa a
  extensão pgvector para armazenamento de embeddings de IA. Tanto o dev quanto a produção
  self-host usam a imagem `pgvector/pgvector:pg16`.
- **Redis** -- Usado para cache, gestão de sessão, persistência de estado de colaboração, e
  intermediação de mensagens entre serviços. O modo dev usa `redis:8.6.1-alpine`; a stack de
  produção self-host gerada pela CLI usa `redis:7.2.3-alpine`.
