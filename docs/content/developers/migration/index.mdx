# Migrando Conteúdo para o Notoriun

Esta seção explica como trazer conteúdo de curso existente para o Notoriun usando a API pública.
Há duas abordagens suportadas:

1. **Migração Programática** -- você programa cada passo (cria o curso, depois os capítulos,
   depois as atividades, depois envia os arquivos). Use isso quando precisar de controle total
   da estrutura resultante -- típico para migrar de outro LMS onde você já conhece o layout de
   capítulo/atividade.
2. **Migração Assistida por IA** -- você envia uma pasta de mídia (vídeos, PDFs, imagens, áudio)
   e o Notoriun pede ao Gemini para propor uma árvore de capítulo/atividade. Você revisa e
   confirma, e um único endpoint cria o curso inteiro em uma transação. Use isso quando você tem
   uma pilha de arquivos mas nenhuma estrutura predefinida.

Ambas as abordagens compartilham o mesmo modelo de dados subjacente -- um Curso contém
Capítulos, e cada Capítulo contém uma lista ordenada de Atividades.

<Callout type="info">
Todos os endpoints abaixo têm o prefixo `/api/v1/`. No desenvolvimento local a URL base é
`http://localhost:1338/api/v1/`. Em produção ela é servida em `/api/v1/` no domínio da sua
instância.
</Callout>

## Autenticação

Toda chamada de migração deve ser autenticada. Há dois tipos de token:

- **Tokens de acesso JWT** (`POST /api/v1/auth/login`) -- uma sessão de usuário, tempo de vida
  de 8 horas, renovável.
- **Tokens de API** (plano Pro) -- com o prefixo `lh_`, emitidos por organização, sem expiração.

Ambos são enviados da mesma forma:

```bash
curl http://localhost:1338/api/v1/courses/?org_id=1 \
  -H "Authorization: Bearer lh_your_api_token_here"
```

Tokens de API são vinculados a uma única organização no momento da criação. Qualquer tentativa
de operar em um `org_id` diferente é rejeitada na camada de autenticação, então um token
vazado não pode alcançar outros tenants.

<Callout type="warning">
**Tokens de API não conseguem chamar todos os endpoints.** Um pequeno conjunto de roteadores --
incluindo os endpoints de migração assistida por IA sob `/api/v1/courses/migrate/*` e vários
endpoints escopados a usuário como `/users/profile` -- rejeitam explicitamente tokens de API
(HTTP 403, `"API tokens cannot access this resource"`). Para essas chamadas, você precisa de um
JWT de usuário. O padrão suportado é a **troca de token pelo admin**: use seu token de API uma
vez para gerar um JWT em nome de qualquer usuário da sua organização, depois use esse JWT para as
chamadas protegidas.

```bash
# Gera um JWT de usuário usando seu token de API
curl -X POST 'http://localhost:1338/api/v1/admin/{org_slug}/auth/token' \
  -H 'Authorization: Bearer lh_your_api_token' \
  -H 'Content-Type: application/json' \
  -d '{"user_id": 1}'
# → { "access_token": "eyJ...", "token_type": "bearer", "user_id": 1, "user_uuid": "..." }
```

O JWT gerado é uma sessão de usuário normal e funciona em todo endpoint, incluindo os endpoints
de migração. O token de API precisa ter a permissão `users.action_read` e o usuário alvo precisa
pertencer à mesma organização.
</Callout>

| Grupo de endpoint | Token de API | JWT |
| --- | --- | --- |
| `POST /courses/`, `PUT /courses/{uuid}`, `DELETE /courses/{uuid}` | ✓ | ✓ |
| `POST /chapters/`, `PUT /chapters/{id}/...`, `DELETE /chapters/{id}` | ✓ | ✓ |
| `POST /activities/`, `/activities/video`, `/activities/external_video`, `/activities/documentpdf` | ✓ | ✓ |
| `POST /blocks/{image,video,pdf,audio}` | ✗ | ✓ |
| `POST /assignments/`, `POST /assignments/{uuid}/tasks` | ✓ | ✓ |
| `POST /courses/migrate/upload` / `/suggest` / `/create` | ✗ | ✓ |

O roteador de blocks tem `Depends(get_non_api_token_user)` no nível do roteador, então mesmo que
os handlers individuais de bloco aceitem usuários anônimos + JWT, um token de API `lh_*` é
rejeitado com `403 "API tokens cannot access this resource"`. O mesmo vale para os endpoints de
migração assistida por IA. Para ambos, use a troca de token pelo admin para gerar um JWT primeiro
(veja o callout acima).

Veja [Autenticação](/developers/api/authentication) para a emissão de tokens.

## O modelo de dados em um diagrama

```
Organization (org_id)
└── Course (course_uuid, course_id)
    └── Chapter (chapter_uuid, chapter_id)
        └── Activity (activity_uuid, activity_id)
            └── (opcional) Block (block_uuid)  ← arquivos de mídia referenciados de uma página dinâmica
```

Duas convenções de ID para manter em mente:

- Strings **`*_uuid`** (ex.: `course_uuid`, `activity_uuid`, `chapter_uuid`) são os
  identificadores públicos usados em URLs e na maioria dos endpoints `GET`.
- Inteiros **`*_id`** (ex.: `course_id`, `chapter_id`) são as chaves primárias internas. Eles são
  exigidos ao **criar** um recurso filho (um capítulo precisa de `course_id`, uma atividade
  precisa de `chapter_id`).

Ambos são retornados em toda resposta de criação, então capture-os conforme avança.

## Tipos de atividade em resumo

| `activity_type` | `activity_sub_type` | O que é | Como o conteúdo é fornecido |
| --- | --- | --- | --- |
| `TYPE_DYNAMIC` | `SUBTYPE_DYNAMIC_PAGE` | Página de texto rico (TipTap / ProseMirror) | Documento JSON em `content` |
| `TYPE_DYNAMIC` | `SUBTYPE_DYNAMIC_MARKDOWN` | Página renderizada a partir de uma URL Markdown remota | `content: { markdown_url }` |
| `TYPE_DYNAMIC` | `SUBTYPE_DYNAMIC_EMBED` | Iframe incorporado (Google Doc, Notion, etc.) | `content: { embed_url }` |
| `TYPE_VIDEO` | `SUBTYPE_VIDEO_HOSTED` | Arquivo de vídeo hospedado localmente | Upload multipart para `/activities/video` |
| `TYPE_VIDEO` | `SUBTYPE_VIDEO_YOUTUBE` | Vídeo do YouTube / Vimeo incorporado | JSON `POST /activities/external_video` |
| `TYPE_DOCUMENT` | `SUBTYPE_DOCUMENT_PDF` | Documento PDF | Upload multipart para `/activities/documentpdf` |
| `TYPE_DOCUMENT` | `SUBTYPE_DOCUMENT_DOC` | Documento genérico | Reservado -- não exposto via endpoint de upload dedicado |
| `TYPE_ASSIGNMENT` | `SUBTYPE_ASSIGNMENT_ANY` | Tarefa corrigida com atividades | Três passos: shell de atividade + registro de tarefa + ao menos uma atividade |
| `TYPE_CUSTOM` | `SUBTYPE_CUSTOM` | Conteúdo estruturado livre | `content` JSON de qualquer formato |
| `TYPE_SCORM` | `SUBTYPE_SCORM_12` / `SUBTYPE_SCORM_2004` | Pacotes SCORM | Reservado -- tratado via o uploader SCORM |

Os esquemas JSON completos de `content` por tipo, incluindo a lista de blocos de página dinâmica,
são documentados na [Referência de Tipos de Atividade](/developers/migration/activity-types).

## Início rápido: os quatro blocos de construção

Uma migração completa se reduz a quatro tipos de chamada, em ordem:

1. **Criar um curso.** `POST /api/v1/courses/?org_id={org_id}` (multipart). Capture
   `course_uuid` e `id` da resposta.
2. **Criar capítulos.** `POST /api/v1/chapters/` (JSON), um por capítulo, passando `course_id` e
   `org_id`. Capture o `id` de cada capítulo.
3. **Criar atividades.** Ou o `POST /api/v1/activities/` genérico (JSON, para shells de
   dinâmica / embed / markdown / custom / tarefa) ou um dos endpoints tipados
   `/activities/video`, `/activities/external_video`, `/activities/documentpdf` (multipart, para
   mídia hospedada).
4. **(Opcional) Envie blocos de mídia** referenciados de uma página dinâmica via
   `/api/v1/blocks/{image,video,pdf,audio}` (multipart) e incorpore-os no conteúdo TipTap da
   página.

Um script bash completo, pronto para copiar e colar, para o fluxo completo está em
[Migração Programática](/developers/migration/programmatic).

## Armadilhas comuns

<Callout type="warning">
**`chapter_id` e `course_id` são inteiros, não UUIDs.** Muitos endpoints `GET` recebem um UUID,
mas todo corpo de `create` quer a chave primária inteira. Leia-a do campo `id` da resposta
anterior, não do campo `chapter_uuid` / `course_uuid`.
</Callout>

<Callout type="warning">
**O tipo de atividade é imutável.** Você não pode mudar `activity_type` ou `activity_sub_type`
depois da criação. Exclua e recrie a atividade se você escolheu o tipo errado.
</Callout>

<Callout type="warning">
**Modificar `content` cria uma nova versão.** Cada `PUT /api/v1/activities/{activity_uuid}` que
toca `content` incrementa o `current_version` da atividade. Isso é normal -- alunos sempre veem
a versão publicada -- mas espere que sua migração deixe um histórico de versões organizado.
</Callout>

<Callout type="info">
**Defina `published: false` durante a migração** e mude para `true` só depois de verificar o
resultado. Atividades não publicadas são retornadas por
`GET /courses/{course_uuid}/meta?with_unpublished_activities=true`, então você pode revisar a
árvore final antes de expô-la aos alunos.
</Callout>

<Callout type="warning">
**Os endpoints de upload tipado (`/activities/video`, `/activities/external_video`,
`/activities/documentpdf`) sempre criam atividades com `published: false`, independentemente de
qualquer campo do payload.** Siga a chamada de criação com
`PUT /api/v1/activities/{activity_uuid}` definindo `{"published": true}` para publicá-las. Só o
`POST /activities/` genérico respeita `published` na criação.
</Callout>

<Callout type="warning">
**`TYPE_ASSIGNMENT` é uma criação em três passos.** Uma atividade de tarefa nua renderiza como um
painel vazio. Você também precisa fazer `POST /api/v1/assignments/` para anexar
título/descrição/correção, e ao menos um `POST /api/v1/assignments/{uuid}/tasks` para uma
interface de envio. Veja
[Referência de Tipos de Atividade -- Tarefas](/developers/migration/activity-types#assignments).
</Callout>

<Callout type="warning">
**`TYPE_CUSTOM` não tem renderizador integrado.** Uma atividade customizada vai aparecer como um
container vazio no visualizador do aluno até que você entregue seu próprio componente React para
ela. Prefira `SUBTYPE_DYNAMIC_PAGE` (TipTap) ou `SUBTYPE_DYNAMIC_EMBED` (iframe) a menos que você
já tenha código de frontend customizado implementado.
</Callout>
