# Diretrizes de Contribuição

Esta página descreve o fluxo de trabalho e os padrões para contribuir com o Notoriun.

## Fluxo de Trabalho

### 1. Fork e Clone

Faça um fork do [repositório do Notoriun](https://github.com/notoriun/learnhouse) no GitHub,
depois clone seu fork:

```bash
git clone https://github.com/YOUR_USERNAME/learnhouse.git
cd learnhouse
```

### 2. Crie uma Branch de Feature

Sempre crie uma nova branch para suas mudanças. Use um nome de branch descritivo:

```bash
git checkout -b feature/your-feature-name
```

Convenções de nomenclatura de branch:

- `feature/` -- Novos recursos ou melhorias
- `fix/` -- Correções de bug
- `docs/` -- Mudanças de documentação
- `refactor/` -- Refatoração de código sem mudanças de comportamento

### 3. Faça Suas Mudanças

Desenvolva suas mudanças localmente usando o
[ambiente de desenvolvimento](/developers/contributing/dev-environment). Mantenha os commits
focados e atômicos.

Ao adicionar ou atualizar dependências:

- **Frontend** -- Use o `bun` para gerenciar dependências JavaScript/TypeScript (ex.:
  `bun add <package>`).
- **Backend** -- Use o `uv` para gerenciar dependências Python (ex.: `uv add <package>`).

### 4. Envie um Pull Request

Envie sua branch para o seu fork e abra um pull request contra a branch `main` do repositório do
Notoriun:

```bash
git push origin feature/your-feature-name
```

Na descrição do seu pull request:

- Explique **o que** sua mudança faz e **por que** ela é necessária.
- Referencie quaisquer [issues do GitHub](https://github.com/notoriun/learnhouse/issues)
  relacionadas.
- Inclua screenshots ou gravações para mudanças de interface.

## Estilo de Código

### Frontend (TypeScript / React)

- Use **TypeScript** para todo código novo.
- Siga os padrões existentes no código para estrutura e nomenclatura de componentes.
- Use componentes funcionais com hooks.
- Formate o código de forma consistente -- o projeto inclui configuração para formatadores de
  código.

### Backend (Python)

- Siga as convenções do **PEP 8**.
- Use type hints para parâmetros de função e valores de retorno.
- Escreva docstrings claras para funções e classes públicas.
- Mantenha as funções focadas e concisas.

## Testes

- Teste suas mudanças localmente antes de enviar um pull request.
- Verifique que a funcionalidade existente não foi quebrada pelas suas mudanças.
- Para novos recursos, inclua testes quando aplicável.

## Processo de Revisão

Depois de enviar um pull request:

1. Um mantenedor vai revisar seu código e pode solicitar mudanças.
2. Trate qualquer feedback enviando commits adicionais para sua branch.
3. Uma vez aprovado, um mantenedor vai mesclar seu pull request.

## Relatando Problemas

Se você encontrar um bug ou tiver uma solicitação de recurso, por favor
[abra uma issue](https://github.com/notoriun/learnhouse/issues/new) no GitHub. Inclua o máximo de
detalhes possível: passos para reproduzir, comportamento esperado, comportamento real, e
quaisquer logs ou screenshots relevantes.
