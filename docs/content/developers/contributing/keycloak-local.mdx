# Keycloak no Ambiente Local

Para desenvolver e testar o [login corporativo](/platform/users/corporate-login), o repositório
inclui um compose completo com Keycloak já provisionado: realm `dev` importado
automaticamente, clients e usuários de teste prontos.

```bash
cp .env.local.example .env    # e troque os segredos marcados
docker compose -f docker-compose.local.yml up -d
curl -sf http://localhost/api/v1/health   # deve responder 200
```

<Callout type="error">
**O primeiro passo não é opcional.** O compose declara `env_file: .env` e falha sem esse
arquivo. Não existe `.env` versionado (é gitignored) — use o
[`.env.local.example`](https://github.com/notoriun/learnhouse/blob/dev/.env.local.example)
como base. Ele já traz as duas variáveis obrigatórias que costumam faltar (abaixo).
</Callout>

## O que sobe

| Serviço | Descrição |
|---|---|
| `learnhouse-app` | Aplicação completa (build local), porta `80` |
| `db` / `redis` | PostgreSQL (pgvector) e Redis |
| `keycloak` | Keycloak 26.x em `start-dev --import-realm`, porta `8080`, admin `admin`/`admin` |
| `keycloak-fwd` | Sidecar socat que encaminha `127.0.0.1:8080` *dentro* do container do app para o Keycloak |
| `mailpit` | Coletor SMTP descartável, porta `8025`. O realm entrega em `mailpit:1025`; use a interface em `http://localhost:8025` para ler o e-mail de verificação |

O sidecar existe para o issuer `http://localhost:8080/realms/dev` resolver igualmente no
**navegador** (host) e na **API** (container) — sem ele, a API não alcançaria `localhost:8080`
e o navegador não resolveria o hostname interno `keycloak`.

<Callout type="warning">
Ao recriar só o `learnhouse-app`, recrie também o sidecar:
`docker compose -f docker-compose.local.yml up -d --force-recreate keycloak-fwd`.
Ele compartilha o namespace de rede do app e fica órfão no container antigo
(sintoma: login corporativo falhando com `sso_indisponivel`).
</Callout>

## Variáveis no `.env`

```env
LEARNHOUSE_KEYCLOAK_ENABLED=true
LEARNHOUSE_KEYCLOAK_ISSUER=http://localhost:8080/realms/dev
LEARNHOUSE_KEYCLOAK_CLIENT_ID=learnhouse
LEARNHOUSE_KEYCLOAK_CLIENT_SECRET=learnhouse-dev-secret

# Obrigatórias e frequentemente esquecidas:
LEARNHOUSE_DEVELOPMENT_MODE=True
LEARNHOUSE_FRONTEND_DOMAIN=localhost
```

<Callout type="warning">
**`LEARNHOUSE_DEVELOPMENT_MODE=True`** — o issuer local é `http://`, sem TLS, e a validação de
URL da API só aceita `http` em modo desenvolvimento.

**`LEARNHOUSE_FRONTEND_DOMAIN=localhost`** — a *redirect URI* do login corporativo é montada a
partir de `hosting_config.frontend_domain`, que **não** cai para `LEARNHOUSE_DOMAIN`. Sem essa
linha o valor vem do `config.yaml` como `localhost:3000`, divergente da URI registrada no client
do realm, e o Keycloak recusa a autorização.

**`LEARNHOUSE_INITIAL_ADMIN_EMAIL` não pode usar TLD reservado** (`.test`, `.example`,
`.localhost`): o validador de e-mail recusa, e a aplicação morre no arranque com `ValidationError`
ao criar o administrador. Use um domínio `.com`.
</Callout>

Lembre-se de habilitar o método **SSO** nos métodos de entrada da organização
(Segurança da organização) para o botão aparecer na tela de login.

## Primeiro acesso não precisa de conta local

<Callout type="info">
Não é preciso criar conta nenhuma antes de entrar. No primeiro acesso pela identidade
corporativa, a conta do LearnHouse é **criada automaticamente** e fica vinculada àquela
identidade; nos acessos seguintes a mesma identidade cai sempre na mesma conta.

Isso vale porque o ambiente local aponta o Keycloak por variáveis de ambiente
(`LEARNHOUSE_KEYCLOAK_*`), ou seja, o **provedor da própria plataforma** — e ali a criação
automática é ligada por padrão. Um provedor de identidade **de terceiro**, configurado por
organização, continua exigindo que a administração habilite a criação automática: uma
organização não passa a admitir gente nova sem ter pedido.
</Callout>

O que continua sendo exigido para a conta ser criada:

- **E-mail verificado no provedor.** `nao-verificado@example.com` é recusado de propósito.
- **Domínio de e-mail permitido**, quando a organização configurou uma lista.
- **Método SSO habilitado** nos métodos de entrada da organização.

A conta criada recebe o papel de **menor privilégio** na organização do fluxo — a criação
automática nunca concede administração.

<Callout type="warning">
Se o acesso for recusado com `conta_nao_encontrada` mesmo com e-mail verificado, o método SSO
provavelmente está desligado nos métodos de entrada da organização, ou existe uma configuração
OIDC por organização (que passa a reger a política em vez do padrão da plataforma).
</Callout>

## Realm `dev` (importado de `docker/keycloak/realm-dev.json`)

- `registrationAllowed: true` e `registrationEmailAsUsername: true` — habilita o
  [registro federado](/platform/users/corporate-login#registro-pela-identidade-corporativa)
  com e-mail como identificador único.
- Client `learnhouse` (confidencial, segredo `learnhouse-dev-secret`, redirect
  `http://localhost/api/auth/keycloak/callback`).
- Client `learnhouse-migration` (service account, para o
  [script de migração](/platform/users/keycloak-migration)) — falta apenas atribuir o papel
  `manage-users` (realm-management) à service account no console admin
  (`http://localhost:8080`), pois papéis não são atribuíveis pelo import.

Usuários de teste:

| Usuário | Senha | Situação |
|---|---|---|
| `teste@example.com` | `teste123` | E-mail verificado — login e registro funcionam |
| `nao-verificado@example.com` | `teste123` | E-mail **não** verificado — útil para testar a recusa na admissão |

## Validação automatizada

As jornadas de identidade corporativa têm uma suíte de aceitação que roda contra este ambiente:

```bash
cd apps/e2e
bun install && bunx playwright install chromium
E2E_BASE_URL=http://localhost \
E2E_ADMIN_EMAIL=<seu admin> E2E_ADMIN_PASSWORD=<sua senha> \
  bun run test:keycloak
```

Ela verifica 7 pré-condições de ambiente antes de qualquer jornada e classifica cada reprovação
como defeito de produto, preparação de ambiente ou indisponibilidade de serviço — de modo que uma
suíte vermelha diz *o que* está errado.

## Solução de problemas

- **`sso_indisponivel` após recriar o app** — recrie o sidecar (Callout acima).
- **Realm não importado** — o import só ocorre na primeira subida do volume; para reimportar,
  `docker compose -f docker-compose.local.yml down -v` e suba de novo (apaga os dados locais).
- **403 em toda entrada corporativa depois de recriar só o Keycloak** — o Keycloak em `start-dev`
  guarda dados em memória, então recriar o contêiner **gera novos `subject`** e invalida os
  vínculos federados já gravados na plataforma. A recusa é correta (nunca revincular identidade
  por coincidência de e-mail). Recrie os dois lados juntos:
  `docker compose -f docker-compose.local.yml down -v && docker compose -f docker-compose.local.yml up -d`.
- **Login corporativo recusado leva a uma página 404** — defeito conhecido: o callback
  redireciona toda recusa para `/auth/login`, que não existe (o caminho servido é `/login`), então
  a mensagem de erro nunca aparece. Para ver o motivo, leia o parâmetro `?error=` na barra de
  endereços.
- **Botão de registro ausente** — confira `registrationAllowed` no realm e se o issuer
  configurado é o da plataforma (registro só existe para o provedor da plataforma).
